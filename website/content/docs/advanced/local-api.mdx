title: "REST API reference"
description: "Read live targets, saved sessions, network information, and aggregated history."

Enable the [Web Server](/docs/settings/local-web-api) first. The default base URL is `http://127.0.0.1:8787`. Localhost Only mode preserves unauthenticated local access. LAN mode requires authentication for every dashboard and API request, including requests made through localhost.

All endpoints below are **GET** and read-only. JSON response properties use camelCase, and enum values are strings. There are no API endpoints to add targets, change settings, acknowledge events, or start/stop monitoring.

## Endpoints

| Path | Response |
| --- | --- |
| `/` | HTML dashboard; redirects unauthenticated LAN-mode browsers to sign-in |
| `/api/targets` | Current engine sessions with options, state, capability, health, and latest snapshot |
| `/api/sessions` | Saved sessions with identifiers, target, destination address, start/stop dates, and sample count |
| `/api/interfaces` | Local interface inventory |
| `/api/neighbors` | Existing OS neighbor cache |
| `/api/gateway` | Object with `gateway`, which can be null |
| `/api/history/{sessionId}` | Aggregated samples and events for a stored session |
| `/api/events/{sessionId}` | Stored events within a date range |

```bash
curl http://127.0.0.1:8787/api/targets
curl http://127.0.0.1:8787/api/sessions
curl http://127.0.0.1:8787/api/interfaces
```

Copy a session `id` from targets or saved sessions for the history and events requests.

## LAN authentication

Copy the server address and newly generated key from **Settings → Web Server**. API clients send `Authorization: Bearer <access-key>` on each request. For example, with the address and key supplied through environment variables:

```bash
curl --header "Authorization: Bearer $PNGR_ACCESS_KEY" "$PNGR_SERVER/api/targets"
```

Set `PNGR_SERVER` to Pngr's displayed address, such as `http://192.168.30.50:8787` (an example only), and `PNGR_ACCESS_KEY` to the full `pngr_` key using your secret-management method. Do not paste a real key into a URL, committed script, shared shell history, or diagnostic output. Avoid curl's verbose/trace output, which can print authorization headers. HTTP transmits both credentials and data unencrypted; use the protections in the [Web Server guide](/docs/settings/local-web-api#http-and-encrypted-access).

Missing or invalid credentials return **401** with `WWW-Authenticate: Bearer`. Repeated authentication attempts can return **429** with `Retry-After`. Keys in query strings are never authentication. There is no endpoint to retrieve a key or change monitoring configuration. Regenerating a key immediately invalidates the previous one and every browser session.

Browser users sign in at `/login` with the same key and use an HttpOnly, SameSite=Strict cookie. Cookies authenticate same-origin dashboard requests without exposing the key to frontend JavaScript. Browser sessions expire after 30 minutes idle or 12 hours total, and are lost when the server restarts. Login and logout use POST forms with CSRF tokens and same-origin checks; logout is available from the dashboard.

## History query

| Parameter | Default | Accepted values |
| --- | --- | --- |
| `from` | One hour ago | Date/time; use ISO 8601 with a timezone |
| `to` | Now | Date/time at or after `from` |
| `hop` | 0 | 0 for destination, or 1–64 for an intermediate hop |
| `maxPoints` | 1200 | 1–10000 |

For example, replace the illustrative session ID with your own:

```bash
curl 'http://127.0.0.1:8787/api/history/00000000-0000-0000-0000-000000000002?hop=0&from=2026-10-14T12:00:00Z&to=2026-10-14T13:00:00Z&maxPoints=1200'
```

History returns `sessionId`, `hop`, `from`, `to`, `sampleCount`, `errorCount`, `truncated`, `points`, and `events`. Points are aggregated across the requested interval rather than being a raw CSV export. `sampleCount` sums point counts and `errorCount` sums local errors. The current endpoint reports `truncated: false`.

## Events query

`from` defaults to 24 hours ago and `to` defaults to now. It returns an array of stored events, including acknowledgment information when present.

```bash
curl 'http://127.0.0.1:8787/api/events/00000000-0000-0000-0000-000000000002?from=2026-10-14T00:00:00Z&to=2026-10-15T00:00:00Z'
```

Invalid session IDs, date ranges, or numeric parameters return **400**. An unknown stored session returns **404**.

## Measurement semantics

Target snapshots include the actual measurement options/epoch, route changes, response kind, and transmission evidence. `lossAvailable` is false when no eligible attempts exist. `applicationServiceAvailable` is true for UDP replies or successful TCP connects, false for UDP Port Unreachable or TCP reset responses, and otherwise null.

UDP target health distinguishes `NoResponse`, `ProbeRejected`, `Reachable`, and `Responded`. ICMP/TCP health can be `Healthy`, `Degraded`, or `Unreachable`; the API's fixed degraded thresholds are 5% response loss, 150 ms average latency, or 30 ms jitter. These labels do not use your display colors or alert thresholds. Paused, stopped, waiting, and local-error states are reported separately.

<Callout title="Response loss is diagnostic">A failed diagnostic response does not establish forwarding loss. Local setup errors are excluded from eligible attempt accounting, and a submitted probe does not prove delivery. A UDP Port Unreachable or TCP reset can establish host reachability while the selected service remains unavailable.</Callout>

## Access and lifetime

Localhost mode binds to IPv4 loopback only. LAN mode adds one selected assigned private address: Automatic chooses a suitable private IPv4 default-route interface, while advanced manual selection also supports unique-local IPv6 and applies authentication to both listeners. Host validation accepts only supported listener hosts, preventing arbitrary hostname access; use the displayed numeric address. There is no permissive CORS configuration. Responses use `Cache-Control: no-store`, and request body/form limits and authentication rate limits bound untrusted input. The dashboard and API require the desktop process to remain open.

The server exposes defined routes and embedded dashboard HTML, not a filesystem directory. All monitoring-data routes are behind the same authentication boundary in LAN mode. Successful authentication grants read access to all available monitoring data; there are no per-client permissions. The desktop GUI and probing engines do not participate in web authentication.

### Reverse proxy requirements

There is no automatic reverse-proxy discovery or trust of forwarded headers. If you operate an HTTPS reverse proxy, enable LAN authentication in Pngr and send requests to an accepted numeric upstream Host (for example, `127.0.0.1:8787`). A public-facing proxy hostname is not an accepted upstream Host.

The proxy must reject cross-origin login/logout requests at its external boundary before normalizing a matching browser Origin to the upstream HTTP origin. Blindly rewriting every Origin would defeat CSRF origin checks. Login and logout also require their CSRF tokens. Rewrite upstream session and login cookies to add **Secure** at the HTTPS edge, while retaining HttpOnly and SameSite=Strict. Pngr adds Secure itself only when its request is HTTPS; it cannot infer TLS terminated elsewhere. Do not enable unvalidated forwarded-header trust to work around this.

Restrict direct HTTP access with firewall rules and keep the upstream connection on loopback or an encrypted protected path. Configure TLS and cookie/origin handling explicitly with your chosen proxy; this version supplies no automatic certificate, proxy, or trust configuration. An ordinary port forward does not add encryption.

For connection failures, confirm the running address and port, the selected interface, device isolation, and firewall rules. See [troubleshooting](/docs/settings/local-web-api#disable-access-and-troubleshoot).
